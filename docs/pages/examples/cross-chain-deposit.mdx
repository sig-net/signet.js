# Depositing Assets on a Foreign Chain

A concrete, end-to-end example of what the [Sign Bidirectional Flow](/architecture/sign-bidirectional) lets you build: an application on one chain (the **source chain**) that custodies and moves ERC-20 tokens living on another chain (the **destination chain**) — with no bridge, no wrapped assets, and no custodian. This exact example ships today as the MPC-custodied ERC-20 vault, implemented on every supported source chain.

## The scenario

A user wants to deposit 100 USDC that lives on Ethereum into your application, which runs on Solana, an EVM chain, or Canton. Your application:

- owns Ethereum addresses through MPC-derived keys — no private key exists anywhere,
- lets the user deposit by sending USDC to an address the application controls,
- credits the user's balance on the source chain only after cryptographic proof that the Ethereum transfer succeeded.

## Walkthrough

### 1. Derive the deposit address

Every `(sender, path)` pair maps to a unique destination-chain key derived from the MPC root key (see [Address Derivation](/architecture/sign-bidirectional#address-derivation)). Your application derives a per-user deposit address off-chain with signet.js — for example path `"0x<user address>"` for the user's deposit address, and `"root"` for the vault's own treasury address — and shows it to the user.

### 2. The user funds it

The user sends 100 USDC to their deposit address on Ethereum with any ordinary wallet. Nothing Signet-specific happens yet — it is a normal ERC-20 balance sitting on an MPC-controlled address.

### 3. Request the transfer signature

The user calls your application's deposit entry point on the source chain. The application builds the exact Ethereum transaction it wants executed — `transfer(vaultAddress, 100e6)` on the USDC contract, with real nonce and fee parameters — records a single-use pending entry keyed by the request ID, and requests a signature via `sign_bidirectional`.

### 4. The MPC signs, the client broadcasts

The MPC threshold-signs the transaction and delivers the signature back on the source chain (`SignatureRespondedEvent`). The client reassembles the signed transaction and broadcasts it to Ethereum — the MPC never broadcasts.

### 5. A verified outcome comes back

The MPC observes Ethereum, extracts the transfer's return value, and publishes a signed outcome on the source chain (`RespondBidirectionalEvent`). Your application's claim entry point verifies that signature against the dedicated response key, checks the transfer returned `true` (and carries no `0xdeadbeef` failure prefix), retires the pending entry, and credits the user 100 USDC of vault balance.

Withdrawals are the mirror image: optimistically debit the balance, sign a `transfer(recipient, amount)` from the vault's `"root"` key, and refund automatically if the verified outcome reports failure.

## Beyond deposits: swaps, yield, anything

Nothing in the flow is transfer-specific — step 3 signs whatever destination-chain transaction your application builds, and step 5 hands back its verified execution result:

- **Swaps**: build a DEX router call (for example `exactInputSingle` on a Uniswap-style router); the verified outcome carries `amountOut`, which your source-chain application can credit or act on.
- **Yield**: build an ERC-4626 `deposit()` into a yield vault; the outcome carries the shares minted. Later, sign a `redeem()` the same way.
- **Anything else**: any transaction an Ethereum account can send, your source-chain application can initiate — and, crucially, verify the result of on its own chain before updating state.

The pattern is always the same: build the foreign transaction → `sign_bidirectional` → broadcast → act on the MPC-verified outcome.
